# 后续方法的公平对比

1. 固定本基线的 HaluMem-Medium 数据文件哈希、3 用户及 28 个原始会话、时间顺序、全部 56 个官方更新点和 75 个问题；不按结果或人工复核结论筛选样本。每个用户从与原生组同等的初始状态开始，逐会话输入同一份原始对话。保持人工诊断记录、参考答案和评分信息不进入记忆写入。
2. 固定用于比较的基础 LLM、embedding、维度、记忆系统配置和工具版本，逐项披露方法不可避免的改动；两组运行时间不同会造成模型别名/服务版本变化，尽可能使用固定版本并记录返回的模型版本。不能仅凭 temperature=0 假定完全可复现。
3. 使用各自同一用户、同一会话后的真实快照；对同一更新点和问题分别按同样 top-10 / top-20、检索模型、上下文格式和问答提示词生成各组结果。不能使用原生组的检索结果或答案充作新方法输出，也不能用未来快照补当前题。题目所要求时间与会话挂载时间有出入时单列并共同复核。
4. 对每组导出相同的官方输入字段，使用同一官方版本的 `evaluation.py`、`eval_tools.py`、评分模型和参数，对提取、更新、QA 均独立评分。冻结评分器、模型、对照范围与分母，记录逐项评分、失败、无效输出和版本指纹；允许逐题配对核查，而不只比较汇总百分比。
5. 保留全部原生异常、空检索、运行失败及其影响，不把失败行偷偷排除。若需要无异常受控对比，事先定义另一个共同子集，两个系统采用同样规则，同时保留全范围结果。已选开发样本的对比用于开发判断；要估计泛化效果，需独立冻结未用于调试的测试集。

本次适配器 `scripts/halumem_official/prepare.py` 是针对既有原生运行记录的转换，不会自动读取新方法的结果；未来新方法需要准备同一官方输入格式，并直接运行同一官方评分入口。官方代码原样保存的逐案记录包含输入、标签和分数，但不保留评分模型的完整原始响应或理由；如果需要更深审计，应在不改变官方评分语义的前提下，提前规划独立的请求记录方式并同样用于两组。
